# F-WP1-014 — One undecodable byte crashed the JSONL boundary and discarded neighbouring rows

Source: fresh-context increment refuter pass over `a107081` (2026-08-13),
verdict `LOW`.

The CLI opened its input in text mode with strict UTF-8
(`open(path, "r", encoding="utf-8")`, and `sys.stdin` for `-`). Text-mode
iteration decodes in ~64 KiB chunks, so a single invalid byte anywhere in a
chunk raised `UnicodeDecodeError` inside `_bounded_lines` — outside the
per-line handler — killing the process with a traceback (exit 1) and
producing no output rows even for valid lines the chunk contained. On a
ready/invalid/ready input the measured output was empty. That contradicted
the boundary law this same increment documented: "parser resource errors
become deterministic per-line results, never process crashes." The failure
was not fail-open (exit was nonzero), hence LOW.

Repair: the transport is now binary end-to-end (`open(path, "rb")`,
`sys.stdin.buffer`); `_bounded_lines` operates on either byte or text
streams with exact byte counting for byte sources; `process_jsonl` decodes
each line individually, so an undecodable line becomes the deterministic
`PREFLIGHT_JSONL_INVALID` per-line result (`REJECTED_INVALID`, exit 2) and
every other row keeps its full result. Blank-line skipping still operates
on the decoded text, so blank/empty-stream semantics (F-WP1-010) are
byte-identical, and `process_jsonl` remains compatible with text sources.
Regression: `TransportDecodeTests.test_invalid_utf8_line_is_a_deterministic_per_line_result`,
`TransportDecodeTests.test_blank_only_byte_stream_still_reports_insufficient_evidence`,
`TransportDecodeTests.test_cli_invalid_utf8_byte_keeps_valid_row_results`.
