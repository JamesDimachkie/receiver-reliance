# F-WP5-002 — multiple responses could desynchronize requests

## Finding

The supervisor returned the first queued response without rejecting a second
line emitted for the same request. That line could be consumed as the next
request's response.

Attempt-2 refutation found a second synchronization error in the same family.
The client incremented its request counter before the request line was fully
written. A child could read one byte of a 1 MiB line, emit `POISON\n`, and
drain the remaining input; that line was incorrectly admitted as the response
for the still-being-written request.

## Correction

Queue order, line count, and phase timing no longer establish identity. The
anonymous stdio stream now carries canonical `RR-SIDECAR/1` binary frames. A
request header binds a positive monotonic sequence, exact payload length, and
SHA-256 of all engine-request bytes. The child reads and hashes the complete
payload, enforces the next sequence, and returns a response frame containing
that exact sequence and request digest plus the exact response length and
SHA-256. The supervisor admits the response payload only after its complete
frame write and flush have returned and every correlation field and payload
digest validates.

`IDLE`, `WRITING`, `AWAITING_RESPONSE`, and `FAILED` remain fail-closed
lifecycle states. They can reject early or unsolicited output but cannot make
an otherwise uncorrelated response valid. Stale, duplicate, reordered, or
digest-mismatched frames terminate the child. No scheduling sleep is used.

This boundary proves host write-and-flush completion and exact envelope
correlation only. It does not claim that a successful Python write proves
child consumption.

## Regression evidence

The recurrence regression uses the refuter's child: `os.read(0, 1)`, emit
`POISON\n`, drain the rest, and remain alive. It runs against a 1 MiB request
with default host writes and 4 KiB chunks. Both runs record one attempt, zero
admitted responses, zero replays, a stopped child, and stopped reader threads.
Depending on platform pipe buffering and reader scheduling, the host's complete
write count may be zero or one; that count is deliberately not identity
evidence. Pre-write and post-write raw `POISON` are also rejected.

Separate probes force valid short writes, a zero-progress write, future and
stale sequences, duplicate frames, wrong request digests, and wrong response
digests. The accepted receipt records 723 checks, 124 requests under one stable
PID, and no stale or mismatched payload admission.
