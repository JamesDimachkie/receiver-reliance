# F-WP5-006 — Confirmed supervision bounds, disclosed and now repaired

Source: Deep Security Scan intake 10 (2026-08-12) findings confirmed by an
independent read-and-probe diagnosis against the attempt-3 bytes
(`csf_96bd9cc0afaa610f981fc462`, `csf_5f0af4f91b622e1ff42ad9b2`,
`csf_d5247a326353d2d0bd4b0c88`, `csf_6dc196be4ba5ff9e6dd98400`,
`csf_ef1156188af8973cc8aac78e`).

**Repaired here:**

- A request header could commit the sidecar to draining and hashing up to
  2^63-1 declared payload bytes (probe: 7.5 GB drained in 4 s for a 0-byte
  response). `rr_sidecar.py` now rejects declarations above
  `MAX_DECLARED_REQUEST_BYTES` (256 MiB) as envelope violations, while
  in-ceiling oversized engine requests keep their correlated `ERR_LIMIT`
  response.
- Transport encoders could emit zero-length frames their own decoders
  reject; both encoders now enforce nonempty payloads (parity with the
  decoders' positivity law).

**Disclosed bounds** — each was a recorded limit of the local supervision
shape, promoted to blocking by the TRUST_MODEL re-adjudication trigger (first
external consumer or any adversarial embedding). All five are now repaired in
the bytes. Each is struck in place rather than deleted, so references to bounds
1–5 elsewhere stay valid:

1. ~~`timeout_seconds` bounds the await-response phase only. The write phase
   is bounded by pipe backpressure and child liveness, not by the deadline:
   a child that never reads can hold the writer in a blocking write until
   the child dies or is externally stopped.~~ **Repaired.** `request()` arms a
   write-phase watchdog for the same `timeout_seconds` the await phase
   already had. On expiry it terminates the process tree first and poisons
   second: killing the child is what returns the blocked write, and it takes
   no lock, so the poison that follows cannot contend with a writer still
   inside its own flush. `write_deadline_count` records that it fired, and
   the request is not replayed. The two phases are bounded separately, so one
   interaction is bounded by twice `timeout_seconds`.
2. ~~Failure cleanup terminates the direct child only; grandchildren spawned
   by a child are not contained (no job object / process group).~~
   **Repaired.** On Windows the child is created `CREATE_SUSPENDED`, assigned
   to a job object carrying `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and only
   then resumed, so no interval exists in which it runs unassigned; the
   initial thread is recovered from a Toolhelp snapshot because `Popen`
   closes its handle before returning. POSIX uses `start_new_session=True`
   and `killpg`. Cleanup terminates the tree before the direct child, and
   does so even when the direct child is already gone — a dead parent is not
   evidence that its children died with it. A child that cannot be bound is
   killed and the failure raised, never downgraded to an uncontained child.
3. ~~A response is admitted when its envelope correlates; asynchronous stderr
   arriving after admission surfaces as a poison on the NEXT interaction
   and at `stop(check=True)`, not retroactively.~~ **Repaired.** Every stderr
   arrival is charged to the interaction it belongs to — the one in flight,
   or the last admitted one when the client is idle — and recorded as a
   `stderr_adjudications` row carrying that sequence and a `retroactive`
   flag. The failure message names that interaction, `state_evidence()`
   carries the adjudications so a receipt records them rather than an
   operator having to reach `stop(check=True)` to learn of them, and `stop()`
   reports them too. The residue is stated rather than implied: a supervisor
   cannot adjudicate bytes it has not yet received. What it can do is charge
   them to the right interaction on arrival instead of to whatever comes
   next, and that is what changed.
4. ~~`grounded-0_4/rr_batch.py` drains an LF-less flood with bounded memory
   but unbounded work, by design: the caller floods only its own local
   transport, and aborting mid-line would break one-response-per-line
   stream consistency.~~ **Repaired by `5946e4c` (2026-08-15); disclosed
   here 2026-08-19.** `_read_request` stops at a 134,283,264-byte
   physical-line ceiling (`8 * MAX_INPUT_BYTES + _READ_CHUNK_BYTES`) and
   raises `BatchRecordLimitError`; `serve` answers with exactly one sealed
   `ERR_BATCH_RECORD_LIMIT` response carrying `request_prefix_sha256` and
   `request_prefix_bytes`, then returns that exit code. The consistency
   objection above was wrong about its own design space: refusing the
   record IS one response for that line, and the prefix fields let the
   refusal name what it saw without claiming a digest of a request it never
   received in full. `grounded-0_4/test_public_surface.py` pins the exact
   bounded read count and the deterministic outcome. Why it stayed
   disclosed for four days: the repair landed inside the window ERRATA E14
   documents, when `perf/sidecar/verify_receipts.py` was exiting 1
   undisclosed, so nothing was reporting the state of these files at all.
5. ~~Execution-input receipts pin file bytes at manifest time (after the
   run), not at each read; a file mutated mid-run is pinned at its post-run
   content. Custody scope wording in `COST_MODEL.md` and F-WP5-001 carries
   this limit.~~ **Repaired.** `_trace_exec.py` records the SHA-256 and byte
   length of the bytes each read opened, guarded so it never records its own
   hashing read. `_evidence.execution_input_manifest` collapses those pins
   per path and fails collection three ways instead of pinning post-run
   content: a read with no pin, two reads of one path that disagree, and a
   path whose manifest-time bytes differ from its read-time pin. Reopening at
   manifest time is now a check, not the pin. The manifest schema is
   `receiver-reliance/wp5-complete-execution-input-manifest-2`, declaring
   `input_pin_time: "read"` and `read_pinned_events`, which
   `verify_receipts.py` requires to equal `repo_open_events`.

**The cost of bound 5, disclosed rather than absorbed.** Read-time pinning
hashes every repository read inside every traced process, so a regenerated
profiling receipt measures a workload that includes that hashing. Post-event
profiling numbers are therefore not comparable byte-for-byte with the
2026-08-12 numbers, and nothing here claims they are.

**Evidence status.** All five repairs are in the bytes. Bounds 1, 2, 3 and 5
move `perf/sidecar/supervised_client.py`, `perf/sidecar/_trace_exec.py` and
`perf/sidecar/_evidence.py`, each pinned byte-exactly by an admitted WP5
receipt, and bound 5 moves the manifest schema those receipts declare. So
`python -B perf/sidecar/verify_receipts.py` reports `checks=133 failures=7`
until a fresh Windows CPython 3.12 profiling and parity run is recorded and
admitted. That red is the mechanism working, not a regression: `perf/SIDECAR.md`
enumerates the seven failures and ADOPTION A6 carries the event.
`perf/sidecar/test_supervision_bounds.py` proves the repairs independently of
that event — `supervision bounds: checks=37 failures=0`, every bound carrying an
arm that fails without the repair.

Scan finding `csf_70114e734b05d246e5745a8d` (no-replay receipt treats a
pre-read marker as acceptance) is **refuted**: the stall adversary consumes
the complete request before writing its marker
(`adversarial_child.py`, stall branch), so the marker is acceptance
evidence by construction.
