# F-WP3-002 — direct deep-pointer containment remained open

Status: **RESOLVED in proposal wording; fresh-context cycle 2 returned
NO-NEW-EVIDENCE.**

The first WP3 refuter reproduced that the proposal closed the compact pointer
budget but still required a complete inline direct RFC 6901 pointer under the
16,777,216-byte output cap. An otherwise-valid request with one additional
property containing 8,388,608 `/` scalars selects a 16,777,217-scalar pointer,
so the ordinary response cannot fit.

Correction: `continuation-specs/GEN_0_5_CORE.md` section 4.1.2 defines the
closed, mutually exclusive `DIGESTED_RFC6901_SHA256_96` representation. The
complete exact pointer is selected first. It remains inline when the ordinary
zero-receipt JCS+LF response fits the cap; otherwise the response contains the
full pointer's SHA-256, scalar and UTF-8 lengths, exact first and last 96
scalars, and raw-request plus decision-input bindings. Error code, class,
precedence, request ID, exit, and self-seal are unchanged. Cap−1/cap/cap+1 and
the slash witness are mandatory acceptance fixtures.

Cycle-2 independent check: exact pointer SHA-256
`629406D23C2E0ECB5731835C833742475C39875DA9839BE7BA00E01EB4163EBB`;
ordinary zero-receipt response 16,777,552 bytes; bounded response 937 bytes.
Selection, hashing, counting, and prefix/suffix retention are stream-computable
without constructing the over-cap response.
