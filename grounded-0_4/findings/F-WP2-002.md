# F-WP2-002 — operation selector namespaces could collide

Status: **RESOLVED locally.** Disposition: **ADDRESSABLE-ADDITIVE**. This was
an authority-query availability and legibility defect. It did not affect the
accepted decision engine, fixtures, or receipts.

## Minimized witness

A structurally valid register could contain two operations shaped as follows:

```json
[
  {"obligation_id":"OBL-A","operation_handle":"SHARED","fields":[]},
  {"obligation_id":"SHARED","operation_handle":"OPR-B","fields":[]}
]
```

The prior validator checked uniqueness inside each namespace independently,
so it accepted this document. A query for `SHARED` then matched both
operations and failed as ambiguous. The symmetric collision (an operation
handle equal to another obligation ID) and a same-row ID/handle collision had
the same root cause.

## Impact

The API promised that either exact selector identifies one operation, but the
validated register shape did not guarantee that property. A future register
extension could therefore pass validation while making the programmatic
authority surface unavailable for the colliding selector.

## Correction

`authority_surface` now requires obligation IDs and operation handles to be
globally disjoint as well as unique within their own namespaces. Cross-
namespace collisions fail during register validation, before any surface can
be returned. The corrected module raw SHA-256 is
`44BA458B93416B48404AAEF19335EA558106A83CA3DD4A65C3F6EE0EDB5ACAA6`.

## Regression commands

```text
python -B grounded-0_4/generate_authority_table.py --check
python -B grounded-0_4/test_authority_legibility.py
```

The legibility suite stages obligation-to-handle, handle-to-obligation, and
same-operation cross-namespace collisions; each must raise
`AuthorityRegisterError` before publication.
